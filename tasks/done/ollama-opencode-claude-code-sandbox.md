# Task: Ollama, OpenCode, and Claude Code Sandbox Setup Scripts

**Status**: done
**Priority**: medium
**Created**: 2026-09-06

## Description

Create AI-related scripts:

1. ai/configure_ollama.sh
- supports macos only
- installs Ollama as a Homebrew service
- configures the Ollama service via its plist with PlistBuddy
- get relevant details from ~/temp/ollama.sh

2. ai/configure_ollama_models.sh
- supports macos only
- get relevant details from ~/temp/ollama.sh
- model: qwen3.8 27B, with two custom model configs - for coding (-code) and for OpenClaw (-claw)
- also pulls qwen3:30b-a3b-instruct-2507-q4_K_M as a transcription model — it's a non-thinking (instruct) model, best suited for summarization (no custom alias needed for it). Replaces the earlier qwen3.5:9b pull.

3. ai/configure_opencode.sh
- supports linux / macos
- points to Ollama at jmac1:11434
- uses the "-code" qwen 3.8 flavor

4. ai/claude-code/Dockerfile — container image for the Claude Code CLI
- installs Claude Code via its native installer, not npm
- embeds rtk (Rust Token Killer, https://github.com/rtk-ai/rtk) for token savings, with its Claude Code hook active by default
- exposes /workspace as the mount point for project code

5. ai/claude-code/run.sh — wrapper script to launch the image (more flexible than docker compose)
- passes the ANTHROPIC_API_KEY env var into the container
- maps the current folder as /workspace in the container
- accepts extra directories to mount as CLI parameters
- looks for a project-local config file (.ajproj / a yaml file) in the current folder; if it has a "volumes:" list, mounts each entry as an additional volume (example: "- ~/repos:/repos")

Scripts should be re-entrant/idempotent as usual for this repo.

**Post-completion addendum (2026-09-13, launcher rework — merged in from a follow-up task rather than left as a separate file):** items 4 and 5 above were reworked after initial completion, in two further rounds:
- **Naming/mechanics:** `ai/claude-code/run.sh` → `ai/claude-code/claude-code-docker.sh` (the old name didn't convey purpose); the script now auto-builds the image if it isn't already built (previously required a manual prior `docker build`); the image is versioned via a plain `ai/claude-code/VERSION` file, tagged as both `ai-claude-code:<version>` and `ai-claude-code:latest`; a `cc-docker` shell alias (`docker/docker.sh`, inside its existing `command -v docker` guard) points at the script.
- **Permissions/naming:** the container runs Claude Code with `--permission-mode acceptEdits` (auto-approves file edits/writes and basic filesystem commands; other tool categories still prompt) rather than `--dangerously-skip-permissions` (rejected as too broad — its own docs recommend it only for no-internet sandboxes, and this container has normal internet access); `claude-code-docker.sh` also passes `--add-dir` for every mounted folder beyond `/workspace`, since Claude Code's own directory scoping is independent of what the container can physically reach. The project-local config filename convention was renamed from `.ajproj`/`.ajproj.yaml`/`.ajproj.yml` to `.aiproj`/`.aiproj.yaml`/`.aiproj.yml` (fixes a likely original typo and matches the `ai/` directory naming).

**Round 4 (2026-09-14) — the user ran `cc-docker` for real for the first time and it worked**, surfacing two remaining rough edges: (a) every run re-asked the theme and folder-trust onboarding questions, since the container is `--rm` and nothing persisted; (b) the container's clock wasn't on host local time. Fixed by: persisting Claude Code's own state (`~/.claude.json` + `~/.claude/`) across runs via host-side bind mounts to `$XDG_STATE_HOME/ai-claude-code` (default `~/.local/state/ai-claude-code`), kept entirely separate from the host's own native Claude Code state; and passing `TZ` through to the container, derived from the host's `/etc/localtime` symlink (works on both Linux and macOS), with `tzdata` added to the Dockerfile so the container actually honors it. `VERSION` bumped to `0.1.1` for the Dockerfile change.

See the updated Acceptance Criteria, Assumptions, and a new Implementation Notes subsection below for the full detail.

## Edge Cases / Test Scenarios

- `ai/configure_ollama.sh` run on Linux: exits 0 with a trace log, no error, no changes made.
- `ai/configure_ollama.sh` run twice consecutively: plist ends up with identical key/value pairs both times (PlistBuddy delete-then-add avoids duplicates).
- Homebrew `opt/ollama` symlink or plist missing: script exits non-zero with a clear, actionable error (mirrors the sanity checks in `~/temp/ollama.sh`).
- Ollama API doesn't come up within the 30-second poll window after restart: script exits non-zero and surfaces `brew services info ollama`.
- `ai/configure_ollama_models.sh` run before Ollama is installed/running: fails fast with a clear error.
- Base model `qwen3.8:27b` already pulled: `ollama pull` does not re-download.
- Base model `qwen3:30b-a3b-instruct-2507-q4_K_M` already pulled: `ollama pull` does not re-download.
- Only one of `-claw`/`-code` aliases exists: script creates only the missing one, leaves the existing one untouched.
- `ai/configure_opencode.sh` run on an unsupported OS (e.g. Windows, BSD): skips cleanly rather than erroring.
- `ai/configure_opencode.sh` run when its config file doesn't exist yet vs. already exists with unrelated settings: creates the file/section as needed without clobbering unrelated keys.
- `claude-code-docker.sh` invoked with `ANTHROPIC_API_KEY` unset: exits non-zero with a clear message, never starts the container.
- Project config file present with no `volumes:` key (only unrelated keys): `claude-code-docker.sh` proceeds with no extra volumes, no error.
- Project config file's `volumes:` entries use `~` for the host home directory: expanded correctly regardless of the invoking user.
- Both `.aiproj` and `.aiproj.yaml` exist in the same directory: `claude-code-docker.sh` picks one deterministically per the documented precedence order, without merging or erroring.
- Extra directory passed as a CLI parameter that doesn't exist on the host: `docker run` surfaces its own mount error; `claude-code-docker.sh` does not need to pre-validate paths.
- Current directory is `$HOME` or another broad path: `claude-code-docker.sh` performs no special-casing — it mounts whatever `$(pwd)` is, same as plain `docker run -v` semantics.
- No image built yet: script builds automatically, tagging both the versioned tag and `:latest`, then runs.
- Versioned tag already present: script skips `docker build` entirely and runs directly.
- `VERSION` bumped after a Dockerfile change: next run's `docker image inspect` misses the new tag, triggering a fresh build.
- `cc-docker` alias is absent from the shell when `docker` is not on `PATH` (existing guard behavior for all aliases in `docker/docker.sh`).
- No extra directories at all (bare `/workspace` run): `claude` is still invoked with `--permission-mode acceptEdits` and no `--add-dir` flags.
